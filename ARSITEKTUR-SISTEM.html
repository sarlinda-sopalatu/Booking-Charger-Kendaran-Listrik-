③ Detail Setiap Microservice

Tanggung jawab, endpoint utama, dan database setiap service

🚪
API Gateway
Port 3000
Pintu masuk tunggal. Verifikasi JWT, rate limiting, dan routing ke service yang tepat. Tidak ada business logic.
JWT Verify Rate Limit HTTP Proxy CORS
📦 Node.js + Express + Redis (rate limit)
👤
User Service
Port 3001
Registrasi, login, manajemen profil, dan penerbitan JWT RS256 + Refresh Token.
POST /auth/register POST /auth/login POST /auth/refresh GET /users/me
🐘 PostgreSQL · ev_users
🔌
Station Service
Port 3002
CRUD stasiun, charger, dan slot waktu. Menyediakan endpoint internal untuk reserve/release slot secara atomik.
GET /stations GET /stations/:id/slots PUT /internal/slots/:id/reserve
🐘 PostgreSQL · ev_stations
📅
Booking Service
Port 3003
Buat/batalkan booking. Menggunakan Saga pattern untuk koordinasi dengan Station & User Service. Publish event ke RabbitMQ.
POST /bookings GET /bookings PUT /bookings/:id/cancel Saga Pattern
🐘 PostgreSQL · ev_bookings
🔢
Queue Service
Port 3004
Antrian digital berbasis Redis Sorted Set (FIFO). Memantau ketersediaan slot setiap 30 detik dan notifikasi user pertama di antrian.
POST /queue/join GET /queue/position/me Redis ZADD/ZRANK Slot Watcher
⚡ Redis · Sorted Set
💰
Payment Service
Port 3005
Inisiasi pembayaran via Midtrans, terima webhook konfirmasi, generate invoice, dan handle refund. Idempotency via Redis.
POST /payments/initiate POST /webhook/midtrans Idempotency Invoice PDF
🐘 PostgreSQL · ev_payments
📊
Monitoring Service
Port 3006
Menerima data OCPP dari hardware charger. Arsitektur CQRS: write ke MongoDB, baca dari Redis cache, broadcast live via Socket.io.
OCPP WebSocket Socket.io Rooms CQRS Pattern Alert Engine
🍃 MongoDB · Time-series + ⚡ Redis
🔔
Notification Service
Port 3007
Pure event consumer — tidak punya REST API publik. Subscribe semua event dari RabbitMQ dan kirim Email (SendGrid) / SMS (Twilio).
Event Consumer SendGrid Email Twilio SMS HTML Templates
📨 RabbitMQ subscriber only

④ Strategi Database per Service

Setiap service punya database sendiri — tidak ada shared schema

Service Database Tipe Tabel / Collection Utama Alasan Pemilihan
👤 User Service PostgreSQL · ev_users Relational users, refresh_tokens Butuh ACID, relasi user ↔ token, query by email
🔌 Station Service PostgreSQL · ev_stations Relational stations, chargers, slots Hierarki station → charger → slot, perlu foreign key & unique constraint
📅 Booking Service PostgreSQL · ev_bookings Relational bookings, booking_events Strong consistency, audit trail event sourcing
🔢 Queue Service Redis In-Memory Sorted Set queue:{stationId}:{date} Operasi ZADD/ZRANK sub-millisecond, TTL 24 jam, atomic pop
💰 Payment Service PostgreSQL · ev_payments Relational payments, invoices ACID untuk transaksi keuangan, audit trail, no data loss
📊 Monitoring Service MongoDB · ev_monitoring Document charger_readings, charging_sessions Write-heavy time-series (1 insert/10 detik/charger), skema fleksibel per tipe charger, TTL 1 tahun
🚪 API Gateway Redis In-Memory Key rl:{ip}, rl:auth:{ip} Rate limit counter — tidak perlu persistent, fast increment

⑧ Architecture Decision Records (ADR)

Dokumentasi resmi setiap keputusan arsitektur yang diambil tim

ADR-001
Microservices Architecture
Pilih Microservices atas Monolith — karena kebutuhan skalabilitas per domain berbeda, isolasi kegagalan, dan tim yang bekerja paralel.
✅ Accepted
ADR-002
Custom API Gateway (bukan Kong/AWS)
Gunakan Node.js + Express custom gateway — kontrol penuh, tidak ada vendor lock-in, familiar bagi tim, dan tidak ada overhead plugin registry.
✅ Accepted
ADR-003
Database per Service
Setiap service punya database sendiri — PostgreSQL untuk transaksional, Redis untuk antrian, MongoDB untuk time-series monitoring. Tidak ada shared schema.
✅ Accepted
ADR-004
RabbitMQ (bukan Kafka)
RabbitMQ dipilih karena DLQ built-in, flexible routing (topic exchange), dan throughput 20-50k msg/s sudah cukup. Kafka overkill untuk skala ini.
✅ Accepted
ADR-005
JWT RS256 + Refresh Token
RS256 (asymmetric) dipilih agar service lain bisa verify token dengan public key tanpa bisa memalsukan token. Refresh token di HttpOnly cookie untuk keamanan XSS.
✅ Accepted
ADR-006
CQRS untuk Monitoring Service
Write path (MongoDB) dan Read path (Redis cache + Socket.io) dipisah karena asimetri ekstrem: 1 insert/10 detik vs ratusan concurrent read oleh dashboard user.
✅ Accepted
ADR-007
Socket.io WebSocket (bukan HTTP Polling)
WebSocket dipilih karena latency rendah, bidirectional, dan efficient. Socket.io menambah room management (1 room per charger) dan auto-reconnect.
✅ Accepted
ADR-008
Saga Pattern untuk Distributed Transaction
Booking service menggunakan Choreography Saga: jika slot berhasil di-reserve tapi booking gagal dibuat, compensating transaction otomatis melepas slot kembali.
✅ Accepted

⑩ Prinsip Arsitektur

Panduan desain yang menjadi fondasi seluruh keputusan teknis

1
Single Responsibility
Setiap service menangani tepat satu domain bisnis. Booking Service tidak boleh menyentuh logika pembayaran.
2
Loose Coupling
Service berkomunikasi lewat API kontrak dan event, BUKAN shared database atau shared object.
3
Failure Isolation
Kegagalan Notification Service tidak boleh menghentikan proses booking atau pembayaran.
4
API First
Kontrak API (OpenAPI spec) didefinisikan sebelum implementasi. Frontend dan backend dapat dikembangkan paralel.
5
Observability
Setiap service menghasilkan structured JSON log, health check endpoint, dan siap untuk tracing dengan Correlation ID.
6
Eventual Consistency
Data antar service konsisten secara eventual melalui event. Strong consistency hanya diperlukan dalam satu service.
7
Infrastructure as Code
Semua infrastruktur didefinisikan dalam Docker Compose — reproducible di environment manapun dengan satu perintah.
8
Defense in Depth
Keamanan berlapis: SSL di Nginx → JWT di Gateway → Role check di Service → Input validation di setiap endpoint.
